## 实际完成

### Block 2 判分口径（`app/backend/scoring_v2.py`）

旧判分要求输出携带标注 `claim_id`，生成式系统不可能满足，任何生成式基线都会被判 0 分
（旧"直接抽取 0.080"即由此而来）。新判分把金标准解析为**文本元素**，按内容比对：
字符二元组定向包含 ≥ 0.50 或 `text-embedding-v4` 余弦 ≥ 0.72 即视为覆盖。
口径见 `docs/experiments/SCORING_PROTOCOL_V2.md`，9 项测试通过。

## 关键结论（详见 `docs/experiments/ERROR_ANALYSIS.md`）

1. **方法相对朴素 RAG 有显著提升**：vs 基线A 整体成功率 +0.1550（Holm p=0.0015），
   内容覆盖 +0.2401，响应方式 +0.2850。
2. **但相对较强基线，整体提升不显著**：剔除 16 条越界样本后，vs 基线B、C 的
   整体成功率差为 +0.022、+0.016，Holm 校正后均不显著。
3. **H3（交互控制）成立**：响应方式准确率 0.280 → 0.565，追问正确率 0.840 → 0.950，
   Holm 校正后显著。
4. **H1（流程中间表示提升覆盖）不成立**：方法的步骤覆盖 0.7565 **低于**基线B 0.8021、
   基线C 0.7926；内容覆盖同样显著更低。据实报告为负结果。
5. **瓶颈已转移到生成层**：方法的最早失效层分布为生成 132、流程 38、检索 30、交互 0。
6. **"过期入口"四个配置 16 次作答全部失败**，无一次选择版本限定响应方式，
   多个配置把历史版本断言为现行规则。

## 数据修复

`PROC_UG_PROOF_PRINT_V001` 与 `PROC_UG_STATUS_CHANGE_V001` 原各仅含一条占位步骤
（"按照官方页面提交…申请材料"），使 200 条样本中约 50 条的步骤指标失效。
经确认校验器未钉住流程记录哈希后，按证据快照改标为真实步骤序列，
声明—步骤绑定同步更新，证据集合未变，`process_version` 升为 0.2.0。
修复后该两类的步骤覆盖率由 0 变为可计算。
