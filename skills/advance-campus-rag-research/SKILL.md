# 推进校园流程感知 RAG 项目（CX26428）

正式名称：《面向校园办事场景的流程感知 RAG 问答方法研究》

甲方：刘金默（暨南大学伯明翰大学联合学院，信息与计算科学）
工作副本：`E:/workbuddy-workplace/大创/_repo_review`（改动经甲方确认后再合并原仓库）

## 0　最高优先级：三条不可让步的原则

任何时间压力下都不放弃这三条。历史上这个项目正是因为没有它们，做出了一个自欺的实验。

**原则一：人工标注必须留在评分侧，不得进入推理链路。**
推理输入只允许是：用户对话、用户提供的槽位、以及本次检索到的来源/证据。任何读取 `gold.*`、`allowed_claims`、`process_id`（来自样本）、`scenario_type`、`difficulty`、`version_risk` 的推理代码都是缺陷，必须修掉。人工标注的流程记录只能用于评分。

**原则二：先修判分口径，再谈模型。**
判分不得依赖"输出携带标注 ID"。必须用要素级集合匹配（步骤/材料/时限/入口/声明要点）＋语义相似度＋引用支持性判定。否则生成模型的自由文本会被判 0 分，实验毫无信息量。

**原则二之补充：判分的每一侧都必须在系统能表达的表示空间里。**
2026-10-15 的返工轮证明，这条只做一半不够：旧缺陷（`claim_id`）修好之后，同一类错误在
`missing_slot_ids`（闭集 ID vs 自由文本）上原样复现了一次。新增任何判分条件，先问一句
**"随便一个能说对的生成式系统，能不能拿到满分？"**，并为它写一条守门测试（见
`tests/test_scoring_v2.py` 的 `test_every_schema_mode_is_reachable`、
`test_free_text_slot_description_scores_full_slot_f1`）。
判分缺陷未修好之前，由它产出的任何"机制有效/无效"结论一律不成立。

**原则三：每个指标必须指向一个可修的动作。**
一个低分要能回答"下一步该改检索、改流程、改核验还是改生成"。不许用笼统总分掩盖故障层。参考 RAGAS / RAGChecker 的模块化诊断思路。`overall_success` 是 7 项精确等于 1 的合取，属最严口径，定位问题时必须同时读分项。

## 1　进入项目后先恢复状态

按顺序执行，不要凭记忆工作：

1. 确认仓库根：`git rev-parse --show-toplevel`。
2. 读本 skill 的 `references/PROJECT_STATE.md` —— 当前进度锚点、已完成/进行中/未开始。
3. 读仓库的 `docs/project/WORK_PLAN_2026-10.md` —— 完整两段式计划与每个 Block 的验收条件。
4. 读本 skill 的 `references/AUDIT_FINDINGS.md` —— 已查实的泄漏点、冗余测试、一次性脚本清单。**这些结论不要重查，直接使用。**
5. 执行 `git log -8 --oneline --decorate` 与 `git status --short`，核对锚点与实际提交是否一致。
6. 只在需要追溯具体结果时读 `docs/work-reports/` 中最相关的一份。

仓库文件是权威状态。聊天记忆与仓库冲突时，以仓库为准。

## 2　工作顺序

严格执行 `WORK_PLAN_2026-10.md` 的 Block 顺序。第一部分的 Block 有严格依赖：

```
Block 1 工程底座  →  Block 2 判分口径  →  Block 3 检索与重排序  →  Block 4 流程抽取器  →  Block 5 四配置对照  →  Block 6 坑题集  →  Block 7 材料
```

Block 2 与 Block 3 不可跳、不可砍。Block 5 的基线 A 与基线 B 不可砍。

每轮开工前写清：本轮目标、输入、允许改动范围、明确不做的范围、可验证的验收条件。**不得把"完善/优化/提升"当作验收条件**，必须改写成可检查的代码、数据、指标或文件。

## 3　明确禁止

- 不得把人工标注当作推理输入（见原则一）。
- 不得新增按测试集问法写死的关键词表、正则表、事项→流程编号映射。路由与意图判定应由证据或模型完成。
- 不得用"某个常量表等于某个字面量列表""样本数恰好等于 N"这类断言作为测试。
- 不得重跑会改写已冻结数据的脚本（详见 `references/AUDIT_FINDINGS.md` 的重跑风险清单）。
- 不得引入知识图谱、多智能体编排、多租户后台等超出立项范围的内容。
- 不得在实验闭环完成前扩充展示性界面。

## 4　每轮收尾（必做）

1. 跑 `powershell -ExecutionPolicy Bypass -File scripts/verify_all.ps1`，确认数据校验与测试通过。
2. 更新 `references/PROJECT_STATE.md` 的进度锚点（哪一步已做、产出文件、下一步）。
3. 仓库侧：在 `docs/work-reports/` 新增一份工作报告；`PROJECT_MEMORY.md` 更新接续点；涉及方向变化时追加 `DECISIONS.md`。
4. 报告里的数字必须能从保存的实验结果文件复算。
5. 不得把"计划"写成"完成"。状态只用：已验证 / 已完成待验证 / 进行中 / 计划 / 阻塞。

## 5　对外材料口径

- 中期检查表、结题报告里的数字，一律来自 `data/experiments/` 下可复算的结果文件。
- 涉及尚未完成的事项，如实写入"存在问题"，不回避、不美化。
- 跨会话续接靠 `references/PROJECT_STATE.md`，不靠聊天记录。
