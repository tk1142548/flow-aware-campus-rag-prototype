# 持续推进校园流程 RAG 项目

## 1. 恢复项目状态

始终先执行：

1. 用 `git rev-parse --show-toplevel` 确认仓库根目录。
2. 阅读根目录 `AGENTS.md`。
3. 阅读 `docs/project/PROJECT_MEMORY.md`，定位当前阶段和最近接续点。
4. 阅读 `docs/project/PROJECT_PLAN.md` 的当前阶段、依赖、交付物和验收条件。
5. 涉及方向、范围、成本、删除或技术路线时，阅读 `docs/project/DECISIONS.md`。
6. 执行 `git status --short`、`git log -5 --oneline --decorate` 和必要的 `git diff`。
7. 只在需要追溯具体结果时读取 `docs/work-reports/` 中最近一份相关报告。

把仓库文件视为权威状态。聊天记忆与仓库冲突时，重新核验仓库；不要用旧对话覆盖新代码或新数据。

## 2. 确定本轮任务

优先执行 `PROJECT_MEMORY.md` 的最近接续点；用户当轮明确指定其他任务时，以用户要求为准，并检查是否改变既有依赖。

开始修改前，写清：

- 本轮目标；
- 输入文件和前置依赖；
- 允许修改的范围；
- 明确不处理的范围；
- 可直接验证的验收条件；
- 风险与回退方式；
- 是否触及必须请示的事项。

不要把“完善、优化、提升、增强”作为验收条件。把它们改写为可检查的代码、数据、指标、文件或行为。

如果依赖未满足：

- 先完成低风险且在范围内的缺失依赖；
- 若依赖会改变核心方向、最终范围、成本或立项内容，暂停并向用户提供问题、选项和影响。

## 3. 执行实际工作

### 3.1 数据工作

- 保留原始来源，禁止用规范化摘要覆盖原文。
- 记录规范网址、来源类型、抓取时间、哈希、发布日期、版本状态和本地快照路径。
- 为证据记录页码、段落、选择器或稳定文本定位。
- 区分原文、规范化声明、人工解释和推断。
- 修改证据时保留审计记录，说明旧值、新值、依据和影响。
- 先定义模式和失败样例，再编写批量处理脚本。
- 对不可确认内容标记证据不足，不补写看似合理的事实。

### 3.2 代码工作

- 先追踪真实调用链、数据流和现有测试。
- 保持改动与本轮验收一一对应，避免顺带重构无关模块。
- 修改行为前先增加能够暴露问题的测试。
- 对外部接口、数据模式和配置变更记录兼容性影响。
- 不覆盖用户未提交或未跟踪的文件。
- 暂未获得重大变更确认时，不大规模删除现有实现。

### 3.3 实验工作

- 先冻结数据版本、划分和指标，再调整方法。
- 为每个研究变量设置公平基线和必要消融。
- 保存配置、随机种子、模型版本、提示版本、原始输出、指标、耗时和费用。
- 防止问题模板、来源版本或近重复样本跨数据划分泄漏。
- 主要结论使用人工金标准或确定性指标；大模型裁判只能作为辅助并记录模型信息。
- 记录负结果。初步实验不支持预期时，重新评估研究问题，不选择性隐藏。

### 3.4 文档工作

- 保持正式项目名称不变。
- 使用“已验证、已完成待验证、进行中、计划、阻塞”标记状态。
- 将事实、解释、假设和计划分开。
- 只把已被代码、数据或实验支撑的能力写成已实现。
- 重要计划调整追加到决策日志，不删除历史原因。
- 不在正式研究产物中暴露内部方案取舍式措辞；用明确的研究范围、方法和实验依据陈述最终内容。

## 4. 测试与验证

按风险选择验证强度，但每轮至少验证直接受影响的表面。

### 数据验证

- 模式校验；
- 主键和外键完整性；
- 日期、版本和来源一致性；
- 原文定位可复核；
- 正反样例；
- 变更前后差异统计。

### 后端验证

- 相关单元测试；
- 接口成功与失败路径；
- 大模型启用和禁用路径；
- 典型、边界、越界和对抗查询；
- 错误信息与日志。

### 前端验证

- 生产构建；
- 查询、追问、拒答、证据和错误状态；
- 前后端模式一致性；
- 必要时进行视觉检查。

### 实验验证

- 数据版本和划分固定；
- 基线与方法使用相同输入和预算；
- 指标可从原始输出重新计算；
- 重复运行或确定性复现；
- 失败样本和统计不确定性保留。

若某项验证因环境、费用或权限无法执行，明确标记为“已完成待验证”或“阻塞”，不得写成通过。

## 5. 记录结果与决策

### 更新推进方案

仅在以下情况更新 `PROJECT_PLAN.md`：

- 阶段状态变化；
- 依赖、交付物或验收条件变化；
- 数据或实验推翻原假设；
- 工作量或风险显著变化；
- 新增或删除长期任务。

在“重要调整记录”中保留日期、原因和影响。

### 更新项目记忆

每轮实质工作结束时更新 `PROJECT_MEMORY.md`：

- 当前阶段；
- 已完成和验证状态；
- 正在进行和下一步；
- 新决策、问题和技术债；
- 重要文件、命令、接口或数据结构；
- 需要用户确认的问题；
- 一个明确、可直接执行的最近接续点。

保持项目记忆精炼。详细过程放入工作报告，不把完整日志复制到记忆。

### 更新决策日志

在 `DECISIONS.md` 追加：

- 会约束后续工作的技术或项目决策；
- 原计划与实际结果冲突；
- 重大选择需要用户确认；
- 暂定决策被证据确认、修改或撤销。

不要改写历史条目以掩盖变化。

### 新增工作报告

在 `docs/work-reports/` 新建：

`YYYY-MM-DD-NNN-short-slug.md`

报告必须包含：

- 本轮目标；
- 状态摘要；
- 实际完成；
- 文件变更；
- 测试、实验或数据校验结果；
- 尚未验证或未完成事项；
- 失败、困难和新问题；
- 对推进方案和决策的影响；
- 需要用户决定的问题；
- 下一轮接续任务。

引用具体命令、退出状态和关键数字。不要只写“测试通过”。

## 6. 自主决定边界

可以自主执行：

- 低风险代码整理；
- 局部缺陷修复；
- 测试、数据模式、校验脚本和文档修正；
- 不改变研究含义的依赖与运行说明整理；
- 已确认阶段内的样本核验和实验执行；
- 对错误事实、夸大表述和失效链接的记录与修正。

必须暂停并向用户确认：

- 改变核心研究方向或正式项目定位；
- 锁定最终事项范围、样本规模或成果形式；
- 大规模删除或替换已有实现；
- 引入显著费用、算力、付费服务或长期维护负担；
- 偏离立项内容或改变对外承诺；
- 处理或推送可能含个人信息、敏感数据或授权不明的材料；
- 发布、提交论文、创建公开仓库或其他不可逆外部动作。

## 7. 处理计划与实际结果冲突

实际证据优先于原计划。

1. 保存失败输出、数据差异或实验结果。
2. 判断冲突是否影响局部实现、阶段验收或核心方向。
3. 对局部、低风险问题直接修正并记录。
4. 对重大问题整理至少两个可行选项、各自影响和推荐依据。
5. 在用户确认前停止重大变更，但继续完成不依赖该决定的安全工作。
6. 更新决策日志、推进方案、项目记忆和工作报告。

不得为了维持原创新点而隐藏负结果，也不得以加大系统复杂度代替可测量贡献。

## 8. 结束本轮工作

结束前逐项确认：

1. 实际工作已经完成，或阻塞原因有证据。
2. 规定验证已执行并记录。
3. `git diff` 只包含本轮授权范围内的修改。
4. 推进方案在需要时已更新。
5. 项目记忆已更新。
6. 已新增工作报告。
7. 下一轮接续点只有一个明确起点。
8. 若修改了本 Skill，运行验证器并通过 `scripts/sync_project_skill.ps1` 更新安装镜像。

向用户汇报结果、证据、未验证项和下一步，不依赖用户阅读中间更新。
